BolsterDesign system

Overview

Getting started

How to find your way around the system as a designer, and how to bring it into a page or a prototype as a developer.

bolster.csstokens.cssbase.csscomponents/tooltip.jsUpdated 2026-10-20

The system is plain CSS: tokens, element defaults and one file per component, with this site, where each part's page shows it live in every variant and state, and a set of concept pages built on top. Designers start with what each part is for. Developers start with one stylesheet.

For designers

Reading this site

  • Principles and Foundations (colour, type, space and the rest) say why things look and work the way they do. Read them first.
  • Components have one page each: when to use the component and what to use instead, its anatomy, variants, sizes and states, do's and don'ts, the words, accessibility, the markup and the tokens it uses.
  • Patterns describe how parts behave together: scrolling, opening records, filtering, bulk actions. Page types show them put together: the list, the to-do, the calendar, the pipeline and the timeline.
  • Every component, pattern and page type carries a status badge (stable, needs work, trying out, draft, not built yet) and ends with what's still open. The backlog gathers everything open in one place. How things move from concept to system explains the statuses.

Specimens and concepts

  • Specimens (system/specimens/) are the components' workbenches: every variant and state working on the system's own CSS, in light and dark. This site is the one documentation (D133): each component's page shows its specimen live under “Every variant and state”, and the backlog's drafts list the parts built in a concept that are waiting for the product designer's approval.
  • The concepts (concepts/index.html) are whole pages, one page type at a time, built from the system with made-up sample data inside a Bolster-style app shell. Each one's “About this concept” dialog says what it settles and what's still open. Nothing in a concept talks to Bolster.

Decisions, and what counts as the spec

  • Every value and behaviour has a numbered decision with its reason in the decision log (D-entries). How things behave is written as contracts in interaction contracts (I-entries). When you wonder why something is the way it is, search for it there.
  • Figma and screenshots are reference, not spec. The design system wins over Figma and screenshots. Figma's research boards record what was looked at and tried. Where a frame and the system disagree, the system is right until a decision changes it.
  • To change the system, propose the change with its reason. It lands as a decision, with its specimen and this site updated in the same pass. See Contributing.

For developers

Install

The package is bolster-ds. Install it from a local clone, or from the private repository if you have access.

# from a local clone
npm i ../path/to/Bolster

# from GitHub (needs access to mumble-jam/bolster-ds)
npm i github:mumble-jam/bolster-ds

Import

system/bolster.css imports everything: tokens, base, every component and the list page pattern. You can also import single files, as long as tokens and base come with them. Components read semantic tokens, and base sets which surface a thing sits on, which buttons and toolbars read.

// everything
import "bolster-ds/system/bolster.css";

// or file by file
import "bolster-ds/system/tokens.css";
import "bolster-ds/system/base.css";
import "bolster-ds/system/components/button.css";
import "bolster-ds/system/components/badge.css";

Without a bundler, link the same file: <link rel="stylesheet" href="…/system/bolster.css?v=604211e8">. Every file declares the layer order before anything else, so the order holds whatever order the files arrive in:

@layer tokens, base, components, utilities;

Markup

  • A component is a class. Its variants, sizes and tones are data attributes, such as data-variant, data-size and data-tone. Each component's page lists its attributes.
  • Component rules are wrapped in :where(), so they have no specificity (the list page's newer parts are still being moved over; see Architecture). One class of your own overrides them, and you never need !important. If a variant is missing, it's added to the system rather than overridden on a page.
  • data-state="hover|active|focus" holds a state still for specimens and these docs. It isn't for product markup.
  • Your own CSS uses semantic tokens only (--color-content-secondary, not --color-pitch-black-700) and none of Tailwind's stock colours. The same rule holds inside system/components/, where a primitive is a bug.
<button class="button" data-variant="secondary" data-size="sm">Customize</button>
<span class="badge" data-status="booked">Booked</span>

.job-meta {
  color: var(--color-content-secondary);
  gap: var(--space-2);
}

Theming

Every semantic colour is written once with light-dark(). The page follows the operating system's setting by default. data-theme on <html> forces one theme. Shadows can't use light-dark(), so tokens.css deepens them in dark with an override. The app shell's chrome (the top bar and the menu) stays dark in both themes.

/* tokens.css */
--color-surface-canvas: light-dark(var(--color-cement-200), var(--color-pitch-black-950));

<html>                    <!-- follows the OS -->
<html data-theme="light"> <!-- always light -->
<html data-theme="dark">  <!-- always dark -->

Fonts

The interface font, Cera Pro, is licensed, so the package doesn't ship it. base.css looks for a locally installed copy. Your app declares its own @font-face for the three weights the system uses (400, 500 and 700; there is no 600). Until it does, text falls back to Inter where it's installed, then the system font. Titles use Space Grotesk, from Google Fonts.

/* your app: point at your licensed files */
@font-face { font-family: "Cera Pro"; src: url("/fonts/CeraPro-Regular.woff2") format("woff2"); font-weight: 400; font-display: swap; }
@font-face { font-family: "Cera Pro"; src: url("/fonts/CeraPro-Medium.woff2") format("woff2"); font-weight: 500; font-display: swap; }
@font-face { font-family: "Cera Pro"; src: url("/fonts/CeraPro-Bold.woff2") format("woff2"); font-weight: 700; font-display: swap; }

<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Space+Grotesk:wght@400;500;700&display=swap">

Icons

Icons are Font Awesome 6 Pro, the set Bolster licenses. The system's CSS doesn't depend on any icon set: components size whatever svg they hold. The concepts draw icons from concepts/shared/icons.js, a subset generated from the Pro packages. It's licensed to Bolster, so keep it inside Bolster's projects.

  • window.BolsterIcons(name, size, { optical }) returns an icon as an SVG string, size pixels tall. Pages usually shorten it to ic. With optical: true, an icon keeps its own size inside a control's icon box, so icons side by side match in ink and line (see Iconography).
  • Icons in the page are Regular. The app shell's chrome draws Light copies under l-<name>. A page never picks the weight.
  • Which icon means what is decided in system/model/icons.json, one icon per meaning.
<script src="concepts/shared/icons.js?v=604211e8"></script>
<script>
  const ic = (name, size = 16, o) => window.BolsterIcons(name, size, o);
  refresh.innerHTML = ic("refresh-cw", 16);
</script>

Tooltips

Every icon without a label has a tooltip. Put data-tip on the icon or its control, and load system/components/tooltip.js once per page. It draws a single tooltip in the top layer, so no card or table clips it. The tooltip appears after a short pause under a mouse and at once on keyboard focus. The element keeps its own name in aria-label, and screen readers don't read the tooltip. Touch screens have no hover, so never put the only copy of something important in a tooltip.

<script src="…/system/components/tooltip.js?v=604211e8"></script>

<button class="button" data-variant="ghost" data-icon-only aria-label="Refresh" data-tip="Refresh">…svg…</button>
<span data-tip="Labor and materials">…svg…</span>

In the React prototype

The semantic tokens use the same names as the React prototype's theme.css, so the prototype and this CSS read the same variables. The breakpoints are Tailwind's (640, 768, 1024, 1280), so the prototype's utilities keep working beside the components. Import the stylesheet once at the app's entry and write the same classes and attributes in JSX.

// main.tsx
import "bolster-ds/system/bolster.css";

// a component
<button className="button" data-variant="brand">Preview and send</button>

Running it locally

From a clone of the repository, install the dev dependencies (Playwright and axe, for the checks), then serve the repository:

npm install
npm run serve        # http://localhost:4178
  • localhost:4178/site/: this site. After changing its sources, the tokens, the decisions or the inventory, rebuild it with node scripts/build-site.mjs.
  • localhost:4178/concepts/: the concepts hub.

Before a change lands, the checks run: npm run contrast after any token change, then npm run pages, npm run test:visual and npm run test:a11y, plus the three browser checks for corners, icons and tooltips. What each one does, and when to run it, is in Contributing: the checks.
