Contributing

How a change reaches the system: a branch and a pull request, a concept before a component, a decision written down with its reason, and the checks that run before anything merges.

The system lives in one private repository. Its main branch is the system as it stands; everything else reaches it through a pull request that's reviewed before it merges. A change is finished when it's built, written down and checked, in the same pull request.

Branches and pull requests

  • Work on a branch: concept/<name> for a concept, system/<what> for a change to system/. Push your branch as often as you like.
  • Pull main into your branch often, so the system you build on is the current one.
  • One kind of change per pull request. A concept's pull request keeps to concepts/<name>/. A system change (tokens, a component, a specimen) goes in a pull request of its own with its D-entry, so it can be reviewed on its own.
  • Never rewrite pushed history. No force-push, no amending a pushed commit: fix forward with a new one.
  • Never commit keys or credentials, the Font Awesome Pro token especially.

To look at your work locally, run npm run serve and open http://localhost:4178.

Numbering decisions on a branch

Decision and contract numbers collide when two branches add one each. On a branch, write D-new and I-new; they get their numbers when the pull request merges.

Generated files aren't merged by hand. For concepts/shared/icons.js and system/specimens/tokens.html, merge their sources (scripts/fa-icon-map.mjs, system/tokens.css) and run the generator again.

Concepts first, then the system

The system is the status quo (D33): new work starts from system/, and a concept that disagrees with it changes the system first.

  1. Build the page as a concept in concepts/<name>/, one page type at a time, from the system's parts and made-up sample data. A concept may carry its own CSS and JS, but its CSS stays on semantic tokens so its parts can move into system/components/ unchanged. Nothing in concepts/ talks to Bolster.
  2. Explain it in the concept's “About this concept” dialog: what it is, its principles, and its open questions.
  3. List each new part as a draft in system/inventory.json (its drafts, shown in the backlog), waiting for the product designer's approval.
  4. Move it into the system once approved: a component file, a specimen, its D-entry (and an I-entry for its behaviour). Then take it off the drafts.

Behaviour is defined once, high up, and inherited, never copied into a page. Before writing behaviour in a page's script, look for it in concepts/shared/ and system/; if a second page needs something a first page has, move it up first. A page passes only what's its own.

The page is the one scroller (D128): a page scrolls down, never a card or a part of one. Headers stick to the page; a part wider than the screen scrolls sideways only. Only what floats over the page scrolls inside itself.

Documenting decisions

When a component decision lands (a direction picked, a change asked for or approved), update everything that documents it in the same change, without being asked:

  • The D-entry in docs/decisions.md: what was decided and why. And the I-entry in docs/interactions.md when behaviour changes.
  • The specimen in system/specimens/, the component's workbench, and its page on this site (site/src/), which shows the specimen live ("specimen" in its front matter); a new specimen also gets its line in specimen.js's map back to its page.
  • The concept's components inventory, where it has one: who decided each part, and when.
  • The inventory (system/inventory.json), when something changes status or a gap closes.

A bug fix isn't a decision: fix it, don't log it. A correction from the product designer's review is logged, though, in pages/corrections.json, in the change that fixes it: the date, the page (or all), what was wrong, the fix, and its kind (reading, rule, design, sample or bug). The system's share of corrections should fall over time.

Icons

Icons are Font Awesome 6 Pro: Regular in the page, Light in the shell's chrome. Which icon means what is the system's, not a page's: system/model/icons.json, one meaning one icon (D58). A new meaning gets a proposed icon, approved before it joins. To add one, pick it on fontawesome.com, add it to scripts/fa-icon-map.mjs, then fetch and build the subset:

node scripts/fetch-fa-icons.mjs ~/fa-pro/icons.json
node scripts/build-icons.mjs ~/fa-pro/icons.json

Fetching needs the team's Font Awesome Pro token, read from the machine's keychain; it's never written into the repository.

Words

Sentence case in everything: headings, buttons, labels, docs. The design system wins over Figma and screenshots, which are reference, not spec.

The checks

Run them before every pull request, and after the change each one names. Each fails loudly and says where.

CheckCommandWhat it does, and when
Contrastnpm run contrastAfter any token change: every text and control pair must pass AA in light and dark.
Built pagesnpm run pagesAfter any change to a rule, the builder, the checker or a model: rebuilds every built page, checks every description, and lists what changed in each, field by field. Read the changes and commit them with the change that made them.
Visualnpm run test:visualAfter any change that can show (CSS, the renderer, a rule): every built page and the concepts at 375, 1024 and 1440 wide, light and dark, against the approved screenshots in tests/screenshots/, to the pixel. A failure names the page and its diff picture (test-results/…-diff.png, changes in red). When the change was meant, approve it with npm run test:visual -- --update-snapshots and commit the screenshots with it. The approved screenshots come from one reference machine; another machine renders other pixels.
Accessibilitynpm run test:a11yRuns axe (WCAG 2.1 A and AA) on the same pages; fails on violations, and counts what axe couldn't decide for a person to check.
Nested cornersscripts/check-radii.jsIn the browser, on each page touched: await import("/scripts/check-radii.js"), then __radii(). Lists corners that don't share a centre with their parent's (D35).
Iconsscripts/check-icons.jsIn the browser: __icons(). Lists icons side by side that don't match in ink and line (D41), and any Light icon outside the shell's chrome.
Tooltipsscripts/check-tips.jsIn the browser: __tips(), at desktop and phone width. Lists every icon without a label that has no tooltip (D52).
Rules pagenode scripts/build-rules.mjsWhenever system/recipes/list/rules.json changes, in the same change, so the rules page is never behind.
Token specimennode scripts/build-token-specimen.mjsRegenerates system/specimens/tokens.html from system/tokens.css.

The three browser checks only see what's on screen: open the menus, sheets, the record and the bulk bar first. Then look at every page touched at 375, 1024 and 1440 wide, in light and dark.

Components reference semantic tokens only: a primitive in system/components/ is a bug.

Updating this site

This site is built, not written page by page in HTML. Its prose lives in site/src/, one fragment per page; everything the system already says is read from where it says it: tokens from system/tokens.css, decisions and contracts from docs/, what exists and what's missing from system/inventory.json.

  1. Edit a page in site/src/, or the inventory in system/inventory.json (a status, a gap, a draft).
  2. Build the site: 
    node scripts/build-site.mjs

The build prints a summary and stops on an error. Never edit the built pages in site/ directly: the next build overwrites them. Run it again after any change to tokens, decisions, contracts or the inventory, so the site never drifts from the system.
