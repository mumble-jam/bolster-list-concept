BolsterDesign system

Foundations

Accessibility

WCAG 2.1 AA is the floor, in light and dark. The system gets there by using the platform (native inputs, dialogs and popovers, tables with links), checks every built page by machine, and leaves a short list to a person.

Stablebase.csstokens.csscomponents/tooltip.jsdocs/interactions.mdUpdated 2026-10-29

Every part of the system meets WCAG 2.1 level AA, in both themes. Most of it comes from building on what the browser already does: a native checkbox is reachable by keyboard and named to a screen reader with no script, a <dialog> traps focus and closes on Escape by itself. What the platform doesn't give, the system writes once, and the checks hold every page to it.

Contrast

Text and controls pass AA against every surface they sit on, in light and in dark: 4.5:1 for text, 3:1 for the edges of controls.

  • Three text levels (D11): primary, secondary and tertiary all clear 4.5:1 on white, the canvas, the sidebar and a selected row. Tertiary is placeholder and caption text; it passes too, so nothing is too light to read.
  • Field borders are 4.0:1 on white, well over the 3:1 a control's edge needs (D7).
  • Pairs that flip get their own token where the plain one wouldn't pass. On a toast, which is dark in light and near white in dark, the brand yellow measured 1.02:1, so the inverse surface has --color-action-brand-on-inverse (D125).
  • Colour is never the only signal. A status badge says its word; a field in error says what's wrong under it.

Run npm run contrast after any token change. It resolves every text and control pair the components use, in light and dark, and fails if one drops under AA.

Focus

One focus ring for everything (D8): 2px in the focus blue, 2px off the element's edge, on :focus-visible, so it shows for the keyboard and not for a mouse click. A field draws it on itself: its border turns blue with a 1px ring around it.

  • Never remove the ring or restyle it locally. Where an element can't show an outer ring, the component draws an equivalent, as the field does.

Keyboard and overlays

Overlays use the platform (D16): dialogs are <dialog> opened with showModal(), menus are popover. Escape, moving focus in, keeping it there, giving it back and making the page behind inert come with them.

OverlayKeyboardFocus
Dialog (I1)Escape closes; Tab cycles insideMoves to the first control, or in a confirmation to the safe choice (“Keep job”); trapped while open; back to the trigger on close
Picker sheet (I2)Typing filters; arrows move through the options; Enter or Done confirms; Escape closes without changing the valueThe search field inside; back to the trigger, which now shows the value

Tooltip (I4)Shows on focus, hides on blurStays on the trigger; a tooltip never traps or covers
  • Focus always comes back (I11). Whatever opened an overlay gets focus when it closes. If it's gone (the row was archived), focus goes to the list's heading, never to the page's body.
  • Triggers say what they open: aria-haspopup="menu" or "dialog", with aria-expanded while it's open.
  • See Focus and keyboard for focus across a whole page.

Lists are tables

A list of jobs, invoices or vendor orders is a <table>, and each row's name is a link stretched over the row (D17). One click or Enter opens the row, and a screen reader can list the rows' links and read each cell with its column's header.

  • Selection is an explicit checkbox, labelled for its row, never a click on the row.
  • Numbers use tabular figures, so money lines up down a column.
  • See Data table.

Native inputs

Checkboxes, radios, toggles and segmented controls are native inputs, restyled (D7). Keyboard, forms, labels and screen readers work with no script.

  • A toggle is a checkbox with role="switch".
  • An error colours the field's border and its helper text, and says what to do. The input has aria-invalid="true" and aria-describedby pointing at the helper, so the message is read with the field.
  • On phones, inputs never draw under 16px, so iOS doesn't zoom the page when one takes focus.

Icons and tooltips

Every icon without a label has a tooltip (D52), whether it's a button or an icon in a table cell. The control keeps its name in aria-label, with the same words; the tooltip is for sighted people and is hidden from screen readers. A tooltip is never the only place something important is said: there's no hover on a phone. See Iconography.

Touch targets

On coarse pointers (a finger), controls get room to be tapped without drawing any bigger (D5), so a table's toolbar stays dense on a laptop and tappable on a phone.

  • Small buttons (32px) get a hit area 44px tall; their width stays as drawn.
  • Menu items, picker options and checkbox and radio rows are at least 44px tall.
  • Toggles are 44px wide.

Reduced motion

With prefers-reduced-motion: reduce, transitions and animations finish at once and smooth scrolling stops. A proposal to keep fades and drop only movement is being tried; see Motion.

What still needs a person

  • A screen reader pass. axe checks names, roles and structure, not whether a page makes sense heard from top to bottom. Try VoiceOver or NVDA on the flows that matter: open a job, filter a list, send an invoice.
  • Text over a sticky column. axe can't measure contrast where elements overlap, such as a table's sticky first column scrolled over its neighbours, and counts it for review instead.
  • The words. Whether a label, an error or a tooltip says what it means. A check can see that a tooltip exists, not that it's right.
  • Touch. Hit areas are 44px for the controls above; nothing checks the rest. Try it on a phone.

What's still open

  • No recorded pass with a screen reader (VoiceOver, NVDA) on the built pages.
  • Text over a table's sticky column is counted by the checks but still needs a person's look.
  • Touch targets are 44 on coarse pointers for small buttons; nothing checks the rest.
  • A small button's touch area grows only in height (D5 says 44): an icon-only small button is 44 by 32 to a finger.
