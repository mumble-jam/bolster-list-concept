BolsterDesign system

Overview

Principles

Eight ideas every decision in the system comes back to. Each one says what it means, what it looks like on a Bolster page, and the numbered decisions it comes from.

The system is a set of choices: what a button is called, what a colour means, what scrolls. These eight principles are what those choices have in common. When a new case comes up and no rule covers it yet, start from them, then write the decision down.

1. Read for meaning, build by rule

A live Bolster page, a screenshot, a brief or a PRD says what exists: the things, their fields and statuses, what people do there and what they look for first. It never says how the new page should look. Pages are made from two written sources: a model of the thing and the intent of the page. The recipe's rules turn those into the page, so two pages of the same type always come out the same way.

  • The vendor orders page starts from system/model/vendor-order.json (what a vendor order is, its lifecycle, its actions) and pages/list/vendor-orders.intent.json (who comes and what they do). The builder writes the page's description. Nobody edits the description by hand.
  • A line that mixes several things is read apart: “Vendor 100001846 #0003” is the vendor's name, then the vendor order's own number.
  • What the source showed but the system decides is written down as not carried: Bolster's column of Next step buttons, a click that only selects a row.
  • Sample data follows the model's lifecycle. A vendor order awaiting approval has a sent date and no approved date. A waiver seen only as None stays None until someone says what else it can be.
  • Anything the evidence can't settle goes into a short survey, never a guess.

2. One meaning, one way

When something means the same thing, it looks and works the same everywhere. People learn it once, and every page after that is easier. Each part is named for what it does, never for how it looks, so the same name always means the same thing.

  • Buttons are named by role: primary, brand, secondary, ghost, danger. Blue is never a button colour. Blue means a link, focus or a selection.
  • One focus ring for every control: 2px in the focus blue, 2px off the edge.
  • One icon per meaning, kept in system/model/icons.json. A new meaning gets a proposed icon, and it's approved before it's used. There are no stand-ins.
  • One scroller: the page scrolls down, never a card inside it. Headers stick to the page.
  • One colour per status: Booked is Bolster's green wherever a job is booked.
  • Weeks start on Monday everywhere. It's one setting, read by the date range picker, the Tasks page's This week and the calendar.

3. The platform first

Where the browser already has a control or a behaviour, the system uses it and styles it instead of rebuilding it in script. Keyboard use, focus, forms and screen readers then work without JavaScript, and they get better as browsers do. Styling is plain CSS in cascade layers, with no build step.

  • Checkboxes, radios, toggles (role="switch") and the segmented control are native inputs, restyled. Short lists use a native <select>.
  • Dialogs are <dialog> opened with showModal(), so Escape, the focus trap, focus return and the inert background come built in. Menus use popover, placed with anchor positioning where the browser supports it.
  • A list is a <table>, and each row's name is a real link stretched over the row. A click or Enter opens it, and Cmd-click still opens a new tab.
  • Where the browser can, the table's column header follows the page with a scroll-driven animation, so it never lags behind the scroll.
  • CSS is layered (tokens, base, components, utilities), with variants as data attributes. To view a specimen, open the HTML file.

4. Accessible from the start

Accessibility is built into the tokens and components, not added in a pass at the end. Every text and control pair is measured in light and dark, every icon is named, and every built page is checked by machine before a change lands.

  • Three text levels (primary, secondary, tertiary). All three reach 4.5:1 on white, the canvas, the sidebar and selected rows. Field borders reach 4.0:1, above the 3:1 minimum for controls.
  • One focus ring that shows on keyboard focus. In the live product, no button style showed focus at all.
  • Every icon without a label has an aria-label and a tooltip with the same words (data-tip).
  • List rows are links in a table, so a keyboard can open them and a screen reader lists them.
  • npm run contrast runs after every token change, and npm run test:a11y runs axe on every built page. When a toast's Undo measured 1.02:1 in dark, it got a token of its own.

5. Colour carries meaning

Surfaces are calm: warm cement neutrals on a paper canvas in light, Bolster's pitch-black greys in dark. Colour goes only where it says something (a status, a warning, a selection, the one step that moves a job forward), and each colour means one thing. Colour is never the only cue: the word comes first.

  • A status badge is its word on a tint, with no dot. The word tells you the status and the colour backs it up.
  • Brand yellow is rare on purpose. It's for the single step that moves a job forward, such as “Preview and send”.
  • Blue is the accent for links, selection and count badges, one blue instead of the six the live product used.
  • Jobs don't get colours of their own. A colour per job is a code people would have to learn, on a platform already full of colour coding. The job's name says which job it is.
  • On the calendar, colour says what kind of thing you're looking at: job work, sales appointments, events (trying out).
  • Every status pair passes 4.5:1 in both themes.

6. Said in the trade's words

The words on screen are part of the design. Labels use the screen's own names in sentence case. Explanations never swap in a synonym. Values read the way contractors and office staff say them, and identifiers keep the format people search by.

  • The page title is the menu item's name, word for word: Job list, not Jobs; Leads and customers, not Customers.
  • An explanation names things as the screen labels them. If it needs a new term, it defines it once in the screen's words: “Won is Booked plus In progress”.
  • Values read as their type (“5 items”, not “5”), and identifiers keep Bolster's format: vendor orders are “#0003”, invoices “Invoice #29599975514”.
  • Bolster's words win. The record's list of events is called Activity, because Timeline is Bolster's name for its schedule page.
  • Sentence case everywhere: “Schedule visit”, never “Schedule Visit” or “SCHEDULE VISIT”.
  • Times and dates as North America writes them: “9 am”, “Oct 7” (trying out).

7. Built for the site and the office laptop

Bolster is used on a phone on a job site, often with one hand, and on a small laptop in the office. Every page works on both. The page is the one scroller, the bars step aside as you scroll and come back on the way up, and the next step stays where a thumb or a pointer can reach it.

  • On phones, a page's create action (“Create job”) floats at the bottom right, where the thumb already is. It shrinks to a + while you scroll.
  • A phone row has four corners and the full name, wrapping to two lines if it needs to. Before, the names were cut short on 24 of 25 job rows.
  • The bars slide away as you scroll down and come back as soon as you scroll up, open a menu or move focus to a field.
  • While you select rows on a phone, the count, Select all and Done stay in reach at any scroll point.
  • The timeline scrolls with the page, to fit a small laptop's screen. A part wider than the screen scrolls sideways, and its scrollbar is pinned to the bottom of the window.
  • Small buttons get a 44px touch area on touch screens without being drawn bigger.

8. Decided once, written down

Every value and every behaviour has a numbered decision with its reason. Every interaction has a contract. Behaviour that two pages share is defined once and inherited. Checks that run on their own hold the system to what was decided, so a change shows its effect on every page before it lands.

  • Decisions are D-entries in the decision log, and interaction contracts are I-entries in the contracts. A decision updates its specimen, its catalog card and this site in the same change.
  • Shared behaviour is defined once, in the app shell: what hides and sticks as you scroll, the filter chips, the nested menus. A page passes in only what's its own.
  • npm run pages rebuilds and checks every built page. npm run test:visual compares them, pixel for pixel, at 375, 1024 and 1440 wide in light and dark. npm run test:a11y runs axe.
  • Browser checks cover what CSS alone can't prove: nested corners that share a centre, icons that match in ink and line, tooltips on every bare icon.
  • Corrections from review are logged with their kind (a misread source, a rule, design, sample data, a bug), and the system's share of them should fall over time.
  • The system is the status quo. New work starts from system/, and a concept that disagrees with it changes the system first.
